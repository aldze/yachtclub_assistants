# Git и GitHub на примере этого проекта

Мини-учебник: что такое репозиторий, как сохранять версии локально и как выложить проект на GitHub. Все команды — из этого проекта, их можно повторять в терминале из папки `yachtclub_assistants`.

## 1. Зачем это нужно

Без git папка проекта — это просто файлы «как есть сейчас». Если вы поправили промпт Лоцмана и ассистент стал отвечать хуже, вернуть вчерашнюю версию можно только по памяти.

Git — это система контроля версий. Она хранит **историю снимков** проекта: каждый снимок (коммит) помнит, какие файлы были, что в них изменилось, кто и когда это сделал и зачем (сообщение коммита). Любой снимок можно посмотреть, сравнить с текущим состоянием или вернуть.

Для нашего проекта это особенно важно:
- промпты и база знаний меняются часто, и после каждой правки мы прогоняем `eval` — git позволяет точно сказать, *какая* правка улучшила или ухудшила результат;
- каждый этап из `CLAUDE.md` (ядро, карточка, оценка, Telegram…) — отдельный коммит, поэтому история читается как журнал работ;
- Claude Code видит историю и может откатить свою же неудачную правку.

## 2. Три слова, которые надо понять

| Понятие | Что это | В нашем проекте |
|---|---|---|
| **Рабочая папка** | Файлы, которые вы видите и редактируете | `prompts/`, `knowledge/`, `app/`… |
| **Индекс** (staging area) | «Корзина» с изменениями, которые войдут в следующий коммит | Сюда кладем командой `git add` |
| **Репозиторий** | База всех коммитов, хранится в скрытой папке `.git/` | Создан командой `git init` |

Цикл работы всегда один: **изменили файлы → `git add` (положили в индекс) → `git commit` (сделали снимок)**.

Индекс нужен, чтобы в один коммит попадало только то, что относится к одной задаче. Например, вы поправили промпт и заодно начали писать код — можно закоммитить сначала только промпт.

## 3. Локальный репозиторий: что уже сделано

Локальный репозиторий — это история, которая лежит **только на вашем компьютере**, в папке `.git/`. Интернет не нужен, никто, кроме вас, ее не видит.

Вот что было выполнено при создании репозитория этого проекта:

```bash
git init -b main                 # создать репозиторий; основная ветка называется main
git add -A                       # положить в индекс все файлы (кроме игнорируемых)
git status                       # посмотреть, что попадет в коммит
git commit -m "Контент проекта: промпты, база знаний, тесты, конфиги"
```

Имя и e-mail автора git берет из глобальных настроек (они у вас уже заданы):

```bash
git config --global user.name    # посмотреть имя
git config --global user.email   # посмотреть e-mail
```

Полезная настройка, чтобы git показывал русские имена файлов буквами, а не кодами вида `\320\235…`:

```bash
git config --global core.quotepath false
```

## 4. `.gitignore`: что НЕ попадает в репозиторий

Файл `.gitignore` перечисляет то, что git должен игнорировать. В нашем проекте:

```
.env                  # секреты: ключ OpenAI, токены ботов
config/*.local.yaml   # реальные данные заказчика (company.local.yaml)
config/*.local.txt    # слова-маркеры заказчика (forbidden.local.txt)
data/                 # база SQLite с диалогами и карточками — там ПДн клиентов
build/                # то, что собирается автоматически
.venv/                # виртуальное окружение Python — у каждого свое
__pycache__/  *.pyc  .pytest_cache/  .DS_Store   # служебный мусор
```

Главное правило: **то, что однажды попало в коммит, остается в истории навсегда**, даже если потом удалить файл. Поэтому ключи, реальные телефоны и названия заказчика должны отсекаться *до* коммита — через `.gitignore` и проверку `python tools/build_docx.py --check`.

Проверить, игнорируется ли файл:

```bash
git check-ignore -v .env          # покажет правило, которое его скрывает
```

## 5. Повседневные команды

```bash
git status                        # что изменено, что в индексе, что новое
git diff                          # построчные изменения, еще не добавленные в индекс
git diff --staged                 # что уже в индексе и войдет в коммит
git add prompts/sales.md          # добавить один файл
git add -A                        # добавить все изменения
git commit -m "Лоцман: уточнен сценарий трейд-ина"
git log --oneline                 # история коммитов, по строке на коммит
git show HEAD                     # что было в последнем коммите
git log -p -- prompts/sales.md    # вся история одного файла с изменениями
```

**Как писать сообщение коммита.** Коротко, в одну строку, *что* и *зачем*: «Этап 1: ядро и CLI», «Боцман: 112 в аварийном сценарии первым шагом». Не «правки» и не «fix».

## 6. Как отменять

| Ситуация | Команда |
|---|---|
| Испортил файл, хочу вернуть как в последнем коммите | `git restore prompts/sales.md` |
| Добавил в индекс лишнее | `git restore --staged app/config.py` |
| Посмотреть, каким файл был 3 коммита назад | `git show HEAD~3:prompts/sales.md` |
| Вернуть файл из старого коммита | `git restore --source=<хеш> prompts/sales.md` |
| Отменить коммит, сохранив историю | `git revert <хеш>` — создаст новый коммит «наоборот» |

Хеш коммита — это короткий код из `git log --oneline` (например, `a1b2c3d`).

Команды `git reset --hard` и `git push --force` уничтожают изменения без возможности вернуть — используйте их, только понимая, что делаете.

## 7. Ветки: этап = ветка

Ветка — это параллельная линия истории. Основная — `main`, там всегда рабочая версия. Новый этап удобно делать в отдельной ветке:

```bash
git switch -c stage-1-core        # создать ветку и перейти в нее
# ... работа, несколько коммитов ...
git switch main                   # вернуться в main
git merge stage-1-core            # влить готовый этап
git branch -d stage-1-core        # удалить ветку, она больше не нужна
```

Если этап не получился — просто вернитесь в `main` и удалите ветку (`git branch -D`), основная версия не пострадает.

## 8. GitHub: удаленный репозиторий

GitHub — это сервис, где хранится **копия** вашего репозитория в интернете (удаленный репозиторий, remote). Зачем:
- резервная копия: сломался ноутбук — проект цел;
- работа с другого компьютера или вместе с кем-то;
- Pull Request — способ показать изменения на проверку (преподавателю, коллеге) до слияния в `main`;
- деплой на сервер (этап 6) удобно делать через `git pull` с GitHub.

Локальный и удаленный репозитории не синхронизируются сами — вы явно отправляете (`push`) и забираете (`pull`) изменения.

### Перед первой публикацией

1. Репозиторий делайте **приватным** (`--private`): в проекте учебная легенда, но в будущем могут появиться реальные данные.
2. Проверьте обезличивание: `python tools/build_docx.py --check`.
3. Убедитесь, что секреты не в индексе: `git ls-files | grep -E '\.env$|local'` — вывод должен быть пустым.

### Создание репозитория на GitHub

У вас установлен GitHub CLI (`gh`). Один раз авторизуйтесь:

```bash
gh auth login                     # GitHub.com → HTTPS → войти через браузер
```

Затем из папки проекта:

```bash
gh repo create yachtclub-assistants --private --source=. --remote=origin --push
```

Эта команда создаст пустой приватный репозиторий на GitHub, привяжет его к локальному под именем `origin` и отправит туда все коммиты.

То же самое вручную, через сайт: github.com → New repository → имя, Private, *без* README → затем:

```bash
git remote add origin https://github.com/<ваш-логин>/yachtclub-assistants.git
git push -u origin main           # -u запоминает связь, дальше достаточно git push
```

### Дальше

```bash
git push                          # отправить новые коммиты на GitHub
git pull                          # забрать изменения с GitHub (если правили на сайте или с другого ПК)
git remote -v                     # куда смотрит origin
```

Ветку этапа можно отправить на GitHub и открыть Pull Request:

```bash
git push -u origin stage-1-core
gh pr create --fill               # PR из текущей ветки в main
```

## 9. Если секрет все-таки попал в коммит

1. **Сразу отзовите ключ** (на platform.openai.com или у @BotFather) — считайте, что он утек. Это главное.
2. Если коммит еще не отправлен на GitHub — уберите файл и перепишите последний коммит:
   ```bash
   git rm --cached .env
   git commit --amend
   ```
3. Если уже отправлен — переписывать историю сложно (инструмент `git filter-repo`), и копии могли остаться в кешах. Поэтому пункт 1 важнее.

## 10. Порядок работы над этапом

```bash
git switch -c stage-2-handoff               # 1. ветка этапа
# 2. работа с Claude Code: «Реализуй этап 2…»
pytest                                      # 3. тесты
python tools/build_docx.py --check          # 4. обезличивание и длина промптов
git status && git diff                      # 5. посмотреть, что меняется
git add -A && git commit -m "Этап 2: карточка передачи"   # 6. коммит
git switch main && git merge stage-2-handoff              # 7. в main
git push                                    # 8. на GitHub
```

Claude Code умеет делать шаги 1, 3–7 сам — достаточно попросить «закоммить этап». Без явной просьбы он не коммитит и не отправляет на GitHub.

| Хочу | Команда |
|---|---|

| История | `git log --oneline` |
| Вернуть файл | `git restore <файл>` |
| Новая ветка | `git switch -c <имя>` |
| Отправить на GitHub | `git push` |
| Забрать с GitHub | `git pull` |
